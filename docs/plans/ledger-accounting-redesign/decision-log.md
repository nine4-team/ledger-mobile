## Derived Implementation Proposals

These are senior-level migration recommendations, not yet user-confirmed product
decisions.

| ID | Proposal | Reason |
|---|---|---|

| P-006 | Add dedicated Supabase/PowerSync staging plus isolated app/MCP configuration. Test Firebase decoding and migration through immutable export fixtures, and repeatedly rehearse the exact import using production-like snapshots. Do not build a Firebase staging version of the redesigned app. | The repository currently defaults app, CLI, scripts, and parts of MCP/Storage to production. Only a fully isolated target lane validates the target architecture without risking production. |
| P-007 | Use expand–migrate–switch–contract in production. Test physical removal in staging, but defer production deletion of legacy fields/collections until after the rollback window. | Target behavior rarely requires immediate physical deletion, and retaining old evidence makes cutover and rollback safer. |

## Clarification: “No Inventory Hop”

For an Item transferred from Project A to Project B for the same Client:

```text
Item.projectId: Project A -> Project B
```

It does not do this:

```text
Project A -> Business Inventory -> Project B
```

The Transfer pair is the audit record. Ledger does not pretend the Client sold
the Item to 1584 and bought it again.

## Clarification: “Combined Spend Does Not Change”

This is confirmed behavior:

```text
Before: Project A $100 + Project B $0   = Client total $100
After:  Project A $0   + Project B $100 = Client total $100
```

It does not mean the Transfer has no effect on each project's budget. It means
the Transfer reallocates one existing amount rather than deleting or duplicating
it.
