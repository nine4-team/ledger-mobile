Ledger MCP — Mental Model

What it is, how a request flows, and why each design decision exists. Click any section to dig deeper.

What is this thing?

An MCP server is a typed tool adapter that lets Claude read and write your Firestore. It runs on Google Cloud Run at a stable URL. Claude (desktop, Code, or the web app) connects to it — you don't call it directly.

Source: mcp-server/ · Stable URL: https://ledger-mcp-351137650087.us-central1.run.app

The one-sentence mental model

Claude calls a tool → the tool wraps Firestore + business logic → the response is shaped for AI token budgets and audit trail → Claude acts on the result.

Lifecycle of a request

Claude (desktop / code) │ │ MCP protocol over HTTP (POST /mcp) ▼ ┌──────────────────────────────────────────┐ │ ledger-mcp (Cloud Run, Node + Express) │ │ │ │ 1. The five design decisions that matter

1. Summary mode by default

Every list_*, search_*, and bulk-getter tool defaults to mode: "summary" — a small curated shape — instead of dumping full Firestore docs.

How it actually works

Shapes are defined once in util/projections.ts: transactionSummary, itemSummary, projectSummary. Tools accept mode: "summary" | "full" and fields?: string[]. After projection, capResponse() serializes items one at a time until a 50 KB budget is hit; anything over returns { truncated: true, hint }.

Why

Tool responses count against Claude's context window. A list of 50 full Firestore transactions is often 30–40 KB of JSON Claude never reads. Summary mode plus the size cap cuts typical responses by ~10× without removing the ability to ask for full docs when needed.

2. Required dated audit notes

Every mutation rejects without a notes field starting with a date (e.g. "4/6 — moved 3 fixtures to Witzenman"). On updates, the new note is appended to existing notes — history is preserved.

How it actually works

requireAuditNote() in util/errors.ts checks notes.length ≥ 8 and the regex /^\s*\d/. Failures return a structured VALIDATION error whose hint tells Claude the exact format. Every create_* / update_* tool calls this before touching Firestore.

Why

Before this, the server's instructions field just asked Claude to include dated notes. Sometimes it didn't. Hard-enforcement with a teachable error means Claude complies after one failure and the audit trail stays clean — no silent backfilling, no (auto) prefixes polluting data.

3. Structured errors with hints

Every tool failure returns { error: { code, message, hint, retryable } } instead of plain text. Claude branches on code; it acts on hint.

How it actually works

Helpers in util/errors.ts: toolError(), notFound(), validation(). Codes are NOT_FOUND, VALIDATION, PERMISSION, CONFLICT, LIMIT_EXCEEDED, UNAVAILABLE. The MCP SDK wraps the result with isError: true.

{
  "error": {
    "code": "VALIDATION",
    "message": "`notes` is required and must be a short dated audit note.",
    "hint": "Include a dated note like \"4/6 — short description of what changed and why\".",
    "retryable": true
  }
}
Why

Plain-text errors forced Claude to string-match ("not found", "missing"). Structured codes let it self-recover without a human: if code === "VALIDATION", read the hint, retry; if NOT_FOUND, re-list and pick a different ID.

4. Dry-run for destructive ops

sell_items, return_items, and move_items_between_projects accept dryRun: true. You get the full plan — the new Purchase/Return/Sale-to-Inventory transaction shape, item updates, source-transaction removals, lineage edges — with zero side effects.

How it actually works

In tools/inventory-operations.ts, each tool computes its plan (including the initial amountCents snapshot and itemIds) and either returns it (dryRun: true) or commits a Firestore batch. Each movement creates a separate transaction rather than mutating a long-lived aggregator. A project-side Purchase from Inventory has one controlled exception: its amount/subtotal follow later effective project-price changes until the item is on a paid invoice.

Why

Sales and returns touch multiple collections (transactions, items, lineage) and are hard to undo. MCP has no mid-call confirmation primitive yet (elicitation/sampling are not widely supported). dryRun gives Claude a way to show its work before committing, and gives you a way to inspect before approving a large move.

5. Telemetry as stderr JSON

Every tool call logs one JSON line to stderr: tool name, success, duration, response bytes, error code. Cloud Run streams stderr into Cloud Logging automatically.

How it actually works

withTelemetry(toolName, handler) in util/telemetry.ts wraps every tool handler. It times the call, JSON-stringifies the response to measure bytes, extracts an error code from structured isError responses, and writes {"event":"mcp_tool_call", ...} to stderr.

Why

Before this, there was zero visibility into what Claude actually reached for. Now you can query Cloud Logging for tool frequency, latency p95, and error rate — which tells you which chains Claude repeats (candidates for new composite tools) and which tools keep failing (candidates for better hints).

Task-shaped tools vs primitives

Most of the MCP surface is primitives — get_transaction, list_items, update_project. On top of those sit a few task-shaped composite tools that collapse common 5–15-call chains into a single intent verb:

reconcile_transactionFetch tx + items, compute audit variance, return concrete suggested fixes with tool names.
create_transaction_with_itemsAtomic batched write — creates a transaction and its items in one call, rolls back on failure.
triage_inboxRanked incomplete transactions with per-row reasons (needs review > missing category > largest amount).
sell_items / return_items / move_items_between_projectsPer-batch immutable inventory movement transactions + lineage edges + dryRun preview. Inventory to project creates a Purchase doc (auto-ID); project-originated items acquired into inventory create a Sale doc; returns to inventory create a Return doc with source: "Business Inventory"; project-to-project moves emit the required hops in one batch.
Why keep the primitives too?

Composites are great for known workflows but terrible for one-off queries and exploratory work. If Claude only needs one field on one item, it shouldn't have to call reconcile_transaction. The principle: composites sit on top, they don't replace.

When something breaks

Symptom: Claude says a tool doesn't exist, or calls one with an old signature.

Check → Fix

Check: Did the last deploy land? Run gcloud run services describe ledger-mcp --region us-central1 --format='value(status.latestReadyRevisionName)'. Check server_info returns the version you expect.

Fix: Redeploy (see Deploy section). Then in Claude, disconnect and reconnect the MCP server — clients cache tool schemas on connect.

Symptom: Every mutation fails with VALIDATION: \`notes\` must begin with a date.

Check → Fix

Check: Claude's note probably starts with a word, not a digit. The regex is /^\s*\d/.

Fix: Nothing to fix server-side — this is working as designed. Claude will retry with a correct format after reading the hint. If it doesn't, tell it to prefix with today's date like "4/7 — ...".

Symptom: A list_* call returns truncated: true and is missing data.

Check → Fix

Check: The serialized response exceeded the 50 KB budget in capResponse(). Look at returnedCount vs totalCount.

Fix: Narrow the query (add filters), or pass explicit fields: ["id", "amountCents"] to shrink each item further, or lower the limit. The hint in the response tells Claude which lever to pull.

Symptom: After a deploy, all OAuth tokens are invalid — Claude has to reauthenticate.

Check → Fix

Check: Did you use --set-env-vars instead of --update-env-vars? --set-env-vars replaces ALL env vars, wiping OAUTH_TOKEN_SECRET. When the secret changes, all signed JWTs become invalid.

Fix: Always use --update-env-vars (see Deploy below). If you already wiped it, reauthenticate in each client — there's no recovery.

Deploy + env vars

Must run from inside mcp-server/ — the service has its own Dockerfile there; running from the repo root triggers generic buildpack detection which fails.

cd mcp-server && npm run build && \
  gcloud run deploy ledger-mcp \
    --source . \
    --region us-central1 \
    --project ledger-nine4 \
    --allow-unauthenticated \
    --update-env-vars FIREBASE_PROJECT_ID=ledger-nine4

CRITICAL: --update-env-vars, never --set-env-vars. The latter wipes OAUTH_TOKEN_SECRET and NODE_ENV=production.

Never create a new Cloud Run service or change the service name. The Claude macOS connector uses a legacy alias URL (ledger-mcp-twpe4tgoja-uc.a.run.app) that routes to the same service. Both URLs must keep resolving.

Required env vars on Cloud Run
  • FIREBASE_PROJECT_ID=ledger-nine4
  • OAUTH_TOKEN_SECRET — stable secret for signing OAuth JWTs. Changing it invalidates all tokens.
  • NODE_ENV=production — ensures the server crashes loudly if OAUTH_TOKEN_SECRET is missing.

For live tool schemas and enums, ask Claude to call server_info and describe_schema — the code is the source of truth, not this doc.
